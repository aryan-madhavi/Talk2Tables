What is Talk2Tables?

Natural Language → SQL → Insights, automatically

Talk2Tables is a Natural Language to SQL web application. A user types a question in plain English — e.g., "Show me top 5 customers by revenue" — and the AI automatically understands which tables to use, writes the correct SQL, executes it safely, and returns results, a chart, and business insights.

Auth flow per request:

  1. 1
    Extract Authorization: Bearer <token> header
  2. 2
    Call verify_request_token() in a thread (Firebase SDK is sync)
  3. 3
    Redis cache check → return immediately if hit (55-min TTL)
  4. 4
    Firestore user check (cache miss only)
  5. 5
    Firestore session check (cache miss only)
Service
auth/services/auth_service.py Auth business logic
FunctionWhat it does
login(id_token, device_info, ip)Verifies Firebase ID token → upserts user in Firestore → creates custom token with role claims → creates session doc → returns {custom_token, session_id, user}
signup(id_token, display_name, ...)Registers a new admin user; creates Organization + user doc in Firestore

🔑
Custom token trick: login() returns a custom token (not the raw Firebase token). The frontend calls signInWithCustomToken(token) — this embeds role and org_id claims so every subsequent request carries them. Firebase tokens live 1 hour, but sessions can be up to 8 hours. Redis caches the decoded token for 55 minutes.

MODULE: access/

Controls which user can query which database, and with what permission
Service
access/services/access_service.py Firestore: user_db_access/{access_id}
FunctionWhat it does
create_access_grant(...)Grants a user access to a DB. Validates org membership for both user AND connection. Blocks duplicates
verify_access(uid, conn_id)THE HOTTEST PATH. Called before every single query. Redis → Firestore. Returns (True, "ok") or (False, reason)
revoke_access_grant(id, uid)Soft delete — sets is_active=False and revoked_at. Cache invalidated IMMEDIATELY (security critical)

verify_access() return codes:

(True,  "ok")                  → access allowed
(False, "no_grant")            → no grant exists at all
(False, "revoked")             → grant.is_active == False
(False, "expired")             → grant.expires_at is in the past
(False, "write_not_permitted") → write required but only "read" granted

🎯
Enum sampling: For VARCHAR/TEXT/CHAR columns with ≤ 20 distinct values, the tool runs SELECT DISTINCT and returns real stored values. The system prompt tells the LLM: you MUST use ONLY these exact values in WHERE clauses. This prevents hallucinated filter values.
Tools
ai_agent/tools/query_tools.py SQL execution with 4-layer safety pipeline

4-layer safety pipeline (in order):

  1. 1
    Injection guard — regex-blocks: ; statement, xp_cmdshell, EXEC(, INTO OUTFILE, SLEEP(), WAITFOR DELAY, BENCHMARK()
  2. 2
    DDL guard — blocks: DROP, TRUNCATE, CREATE, ALTER, RENAME, GRANT, REVOKE
  3. 3
    RBAC write check — INSERT/UPDATE/DELETE/MERGE require role in {admin, power_user, db_manager}
  4. 4
    Auto-LIMIT — SELECT queries without a LIMIT get LIMIT 1000 appended automatically
💡
Full data cache trick: The tool fetches up to 10,000 rows but sends only a 3-row preview back to the LLM (saves tokens). Full rows are stored in _full_result_cache (in-memory, keyed by MD5). The output_parser pops from this cache — avoiding a second DB roundtrip.

Key Concepts (Q&A)

Common interview / viva questions answered in depth
Q1
What is LangGraph and why did you use it?

LangGraph is a framework for building stateful, multi-step AI workflows as directed graphs. We use it because:

  • It manages the flow entry → react_agent → output_parser with conditional routing
  • It supports retry loops — if the LLM returns invalid JSON, the graph automatically loops back to the react_agent (up to 3 times)
  • The StateGraph pattern makes error states explicit — any node can set error_message and route to END immediately
  • Built on LangChain, giving us tool-calling abstraction
Q2
What is the ReAct pattern?

ReAct = Reasoning + Acting. The LLM alternates between:

  1. Thought — decides what to do
  2. Action — calls a tool (e.g., get_schema_list, execute_sql)
  3. Observation — reads the tool's output
  4. Repeats until it has enough information to answer

In our system, create_react_agent(llm, tools) implements this loop internally. The LLM autonomously decides when to call which tool.

Q3
How does the two-tier cache work?
1. Redis
~1ms hit → return immediately
2. Firestore
~80ms · populate Redis → return
3. Live DB
variable · write back to both

Cache TTLs are short (2 min) for security-sensitive data (access grants) and long (1 hour) for stable data (schema). Cache is invalidated immediately on write — revoked access takes effect instantly.

Q4
How is SQL injection prevented?
  1. Input-level regex in _check_injection() — blocks EXEC(, xp_cmdshell, SLEEP(), INTO OUTFILE, semicolons followed by other statements
  2. DDL blocking — DROP, CREATE, ALTER, TRUNCATE are always blocked regardless of user role
  3. Parameterized execution — SQLAlchemy uses text() with bound parameters, never string concatenation

Additionally, LIMIT 1000 is auto-added to any SELECT without a limit.

Q5
What is the RBAC system? 
analyst    (0) — read-only SELECT on explicitly granted DBs
power_user (1) — SELECT + write on granted DBs
db_manager (2) — manage connections and grants
admin      (3) — unrestricted access to everything

RBAC is enforced at three independent layers:

  1. FastAPI dependency (require_min_role) — checks the JWT claim at the HTTP layer
  2. Agent prompt — the system prompt tells the LLM what the user can/cannot do
  3. Tool layer — execute_sql independently re-checks the role before any write operation
Q6
How does multi-tenancy work?

Every resource document in Firestore has an org_id field. All Firestore queries filter by org_id:

  • Users belong to one org
  • Database connections belong to one org
  • Access grants validate that both the target user AND the target connection belong to the requesting admin's org
  • Redis cache keys are scoped: connections:list:{org_id} — so Org A never sees Org B's connections
Q7
How does SSE streaming work?
  1. FastAPI returns a StreamingResponse with content-type text/event-stream
  2. The backend iterates agent.astream_events(...) from LangGraph
  3. On on_chain_start → entry: yields event: progress "Connecting to database…"
  4. On on_tool_start → get_schema_list: yields event: progress "Loading schema…"
  5. On on_tool_start → execute_sql: yields event: progress "Executing SQL…"
  6. On on_chain_end → LangGraph: yields event: result with full data
  7. Phase 2 insights are yielded as event: insights

The frontend's executeQueryStream() reads the ReadableStream body, splits on \n\n, parses each event block, and fires callbacks (onProgress, onResult, onInsights).

Q8
What is the system prompt and why is it important?

The system prompt is the instruction set injected into the LLM at the start of every conversation. It:

  • Tells the LLM which tools are available and how to use them in mandatory order
  • Specifies the exact JSON schema the LLM must return (title, sql_query, summary, total_records, data)
  • Enforces that the LLM MUST call execute_sql (never fabricate results)
  • Contains dialect-specific SQL syntax hints (MySQL vs PostgreSQL differences)
  • Injects the user's role permissions (analyst = read-only, power_user = write with confirmation)
  • Handles edge cases: conversational questions (no tools), out-of-scope queries (reject), write confirmations
Q9
How does the output parser retry mechanism work?
  1. node_output_parser tries to json.loads() the LLM's output
  2. If parsing fails (e.g., LLM returned plain text instead of JSON):
    • If retry_count < max_retries (3): increments retry_count and returns state WITHOUT final_response
    • The graph router sees no final_response + retry_count > 0 → routes back to react_agent
    • A nudge message is added: "Your previous response was not formatted correctly. Return ONLY valid JSON…"
  3. If retry_count >= max_retries: returns error response
Q10
Explain the chat/conversation memory system.

Each user has a workspace per database connection. Within each workspace, they can have multiple chats. Each chat stores messages as a Firestore sub-collection.

Before each query, get_messages() fetches the last 12 messages (6 conversation turns) from Firestore. These are injected as HumanMessage/AIMessage objects into the LangGraph agent's initial state — giving it conversational context.

After each query, append_messages() writes both the user's question and the AI's full response atomically in a Firestore transaction. Message IDs use a turn-prefix system: u_0001, a_0001, u_0002, a_0002… ensuring predictable ordering.

Q11
What happens behind the scenes when a user types a question?
  1. 1
    Frontend calls executeQueryStream() with {connection_id, chat_input, chat_id}
  2. 2
    Backend calls get_or_create_chat() + get_messages() for history
  3. 3
    run_agent_stream() is called. Two pre-flight guards run (write-intent check, in-flight dedup)
  4. 4
    entry_node verifies access grant → fetches decrypted DB credentials → builds SQLAlchemy URL
  5. 5
    LLM calls get_schema_list → gets list of all tables
  6. 6
    LLM calls get_table_definitions → gets column definitions + sample values for relevant tables
  7. 7
    LLM constructs SQL → calls execute_sql → gets results (3-row preview + full in cache)
  8. 8
    output_parser_node parses JSON, pops full data from cache, yields event: result
  9. 9
    Phase 2: asyncio.gather() calls two Gemini functions in parallel → yields event: insights
  10. 10
    append_messages() writes both messages to Firestore in one atomic transaction
  11. 11
    Frontend renders: data table, chart tab, insights tab, history item
